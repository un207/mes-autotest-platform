# MES 自动化测试平台

[![MES 接口自动化测试](https://github.com/un207/mes-autotest-platform/actions/workflows/api-test.yml/badge.svg)](https://github.com/un207/mes-autotest-platform/actions/workflows/api-test.yml)

面向 MES（制造执行系统）场景的自动化测试实践项目。工程按职责拆为四个独立部分：被测系统、测试框架、设备模拟器、管理界面。

| 目录 | 职责 | 说明 |
|------|------|------|
| [`mes-platform/`](./mes-platform) | 被测系统 | 迷你 MES 后端，覆盖工单、报工、质检、物料追溯、设备数采五条业务线。Spring Boot 3.2 + MyBatis-Plus + MySQL 5.7 |
| [`mes-autotest/`](./mes-autotest) | 测试框架 | 接口自动化，pytest + requests + PyMySQL，99 条用例，关键用例采用接口返回与落库双向断言 |
| [`mes-simulator/`](./mes-simulator) | 设备模拟器 | 以 Modbus TCP 模拟产线设备，向 MES 上报数据，并提供六种故障注入用于验证质量把关 |
| [`mes-console/`](./mes-console) | 管理界面 | Vue 3 + Element Plus，将后端 24 个接口组织为可视化操作界面 |

四个工程物理分离而非合并为单体，目的是保持测试的独立性：业务系统与测试框架共处一个工程时，测试容易退化为对自身实现的重述，断言失去外部参照。

---

## 项目缘起

项目的选型起点是一个具体的问题域，而非通用技术练习。

制造现场的一张生产订单要依次经过下单、派工、报工、质检、追溯、关闭六个环节，MES 承担的正是这条链路的记录与约束职责，同时还要接住设备侧上报的产量、温度等工艺数据。这条链路有一个区别于普通业务系统的特征：数据一旦写入错误，事后追溯的成本极高。报工数量与合格数量不守恒时，良率统计与成本核算会同步失真；原料批次若绑定到错误的工单，出现质量问题时无法定位到具体来料。这类错误的共同点是发生时不报错，只在几天甚至几周后的报表里以异常数字的形式浮现。

据此确定项目的核心目标为两条：把业务规则写成可执行的代码约束，让非法数据在入口处即被拒绝；用自动化用例覆盖每一条规则，使规则被改动破坏时能在提交阶段被发现。

## 架构设计

四个工程的关系是围绕被测系统展开的单向依赖：

```
                    MySQL 5.7
                        │
                 mes-platform  ←── 唯一被测对象，业务规则与数据校验的落点
                 ↑      ↑      ↑
                 │      │      └────────── mes-simulator   向数采接口上报设备数据
                 │      └───────────────── mes-autotest    调用接口并回查数据库
                 └──────────────────────── mes-console     读取数据供人工操作
```

被测系统是整个架构的枢纽，其余三个工程都以它为依赖终点。三者之间不存在依赖关系，可独立启停。

系统内部运行三条数据链路，写入两个物理隔离的数据库：

| 链路 | 触发方 | 写入库 | 数据留存 |
|------|--------|--------|----------|
| 业务主链路 | 人工操作或接口调用 | `mes` | 留存，属真实业务数据 |
| 设备数采链路 | 采集器周期轮询 Modbus | `mes` | 留存，含异常数据留痕 |
| 测试验证链路 | pytest 或 CI 触发 | `mes_test` | 跑完自动清场 |

业务库与测试库结构完全一致但物理隔离。测试过程会大量造数，写入业务库会污染人工查看与演示用的数据，因此框架在启动前强制校验库名以 `_test` 结尾，并交叉验证接口实际写入的库与框架回查的库为同一个。

## 测试设计

### 规模与分布

| 模块 | 用例数 | 覆盖重点 |
|------|--------|----------|
| 服务自检 | 3 | 存活与就绪探针、接口和直连的库版本交叉校验、未匹配路由的 404 |
| 工单主链路 | 1 | 建单至关闭的完整流程，每步含落库断言 |
| 工单业务规则 | 36 | 数量守恒、超报拦截、状态机、参数校验、分页边界 |
| 质量检验规则 | 19 | 结论推导、不良代码必填、批次关联一致性 |
| 物料批次与追溯 | 10 | 批次状态流转、防改绑串线、双向追溯、节点顺序 |
| 设备数采质量 | 24 | 三层质量把关、批量边界、异常数据捞取 |
| 统计报表 | 6 | 总览口径反算、日报区间筛选、低良率排行 |
| 合计 | 99 | 冒烟 10 条、回归 89 条、需落库校验 60 条 |

### 三条设计原则

**接口断言与落库断言并用。** 接口返回 HTTP 200 只说明请求到达了业务层，不代表数据已正确持久化。关键用例在断言响应字段之外，另直连 `mes_test` 回查：接口声称报工 120 件，则 `finished_qty` 必须为 120，报工记录条数必须为 1，追溯节点必须已落库。这层校验能捕获事务未提交、字段映射错误、级联写入遗漏等仅靠响应无法发现的问题。

**用例可重复执行且自动清场。** 所有业务编码携带当轮唯一前缀，重复执行不会撞唯一键。造数统一经过工厂方法并登记单号，会话结束时按登记单号精确删除；在此之外再按时间窗兜底扫描一次，捞住绕过工厂直接调用接口产生的数据。排障时可关闭清场以保留现场。

**故障注入验证把关有效性。** 质量把关逻辑只接收正常数据时，其分支永远不会被执行，等于没有实现。设备模拟器提供过热、状态码非法、传感器故障、乱码上报、产量超上限、时钟漂移六种故障形态，逐一验证 MES 是否识别、标记是否正确、原因是否指向准确。详细设计见 [`mes-simulator/README.md`](./mes-simulator/README.md)。

## 使用方式

### 环境要求

JDK 17、Maven 3.9+、MySQL 5.7、Python 3.13+、Node.js 22+。

### 初始化与启动

```bash
# 1. 建库建表（业务库 mes 与测试库 mes_test）
cd mes-platform/sql
mysql -uroot -p < 01_create_database.sql
mysql -uroot -p mes < 02_schema_mes.sql
mysql -uroot -p < 03_schema_mes_test.sql
mysql -uroot -p mes < 04_seed_demo.sql      # 可选，导入演示数据

# 2. 启动被测系统，等待 /api/ready 返回 UP
cd ../mes-platform
mvn spring-boot:run

# 3. 执行接口自动化用例
cd ../mes-autotest
pip install -r requirements.txt
pytest
python tools/run.py                          # 一键执行并生成三类报告

# 4. 启动设备模拟器，产生工业数据
cd ../mes-simulator
pip install -r requirements.txt
python run.py --self-check                   # 先自检，无需 MES 在跑
python run.py                                # 正常运行并持续上报

# 5. 启动管理界面
cd ../mes-console
npm install
npm run dev                                  # http://localhost:5173
```

完整的启动顺序、IDE 配置与常见问题处理见 [`docs/使用手册.md`](./docs/使用手册.md)。

## 持续集成

流水线定义于 `.github/workflows/api-test.yml`，包含两个并行作业：

```
接口自动化回归作业
  MySQL 5.7 容器 → 建库 → 构建被测系统 → 以 test profile 启动 → 轮询就绪
    → 99 条接口用例（含落库断言）
    → 设备模拟器自检（Modbus 通路、设备逻辑、异常注入）
    → 设备模拟器端到端验证（模拟器 → MES 数采 → 质量判定）
    → 生成三类报告 → 回写执行历史 → 归档产物

管理界面构建作业
  安装 Node → npm ci → 构建 → 校验构建产物
```

界面前端与后端关注点不同，也不依赖数据库，因此独立为单独作业并行执行。

三类触发方式：推送或拉取请求时按路径过滤后全量执行；手动触发可选全量或仅冒烟；每日北京时间 06:00 定时全量执行，用于发现环境漂移引起的慢性问题。CI 环境的 MySQL 版本与本地保持一致（均为 5.7），避免出现本地通过而 CI 失败的版本差异问题。

通过率趋势由 `mes-autotest/history/api-test-history.jsonl` 累积，该文件随仓库提交；CI 每轮结束后将新记录回写仓库，使本机与 CI 的执行记录汇入同一条趋势线。

## 已知边界

- 定位为单机实践项目，未做高并发设计。并发正确性依靠工单行锁（`SELECT ... FOR UPDATE`）保证，未引入分布式锁
- 未接入真实产线设备，设备侧数据由 Modbus 模拟器产生，协议实现仅覆盖功能码 3
- 认证与授权尚未实现，接口与管理界面均为开放访问
- 用例按顺序执行设计，不支持多轮并发执行，清场逻辑的时间窗兜底基于该假设
