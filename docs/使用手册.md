# 使用手册

本文档说明 MES 自动化测试平台的部署顺序、IDE 配置与常见问题处理。

---

## 一、工程角色

项目由四个工程组成，职责与依赖关系如下。

| 工程 | 定位 | 面向对象 | 技术栈 |
|------|------|----------|--------|
| `mes-platform` | 被测的业务系统 | 工单员、质检员、仓管等业务角色 | Java 17 + Spring Boot + MySQL |
| `mes-console` | 操作界面 | 同上，日常操作的入口 | Vue 3 + Element Plus |
| `mes-autotest` | 自动化测试用例库 | 测试与开发，用于验证规则未被破坏 | pytest + requests |
| `mes-simulator` | 产线设备模拟 | 为系统提供工业数据来源 | Python + Modbus TCP |

依赖关系为围绕被测系统展开的单向结构：

```
        MySQL（最先就绪）
           │
     mes-platform  ←── 核心，其余三个工程均依赖它
      ↑    ↑    ↑
      │    │    └── mes-simulator   向数采接口上报设备数据
      │    └─────── mes-autotest    调用接口并回查数据库
      └──────────── mes-console     读取数据供人工操作
```

`mes-platform` 与 MySQL 是运行前提，必须先就绪。其余三个工程互不依赖，可独立启停。

## 二、数据流通

系统内部运行三条数据链路，写入两个物理隔离的数据库。

### 链路一：业务主链路

```
   管理界面 / 接口调用 / 测试用例
              ↓
   创建工单 → 派工 → 批次绑定 → 报工 → 质检 → 关闭
              ↓
        写业务库 mes
              ↓
   同时追加一条追溯流水记录（只增不改）
```

每完成一步业务操作，系统同时执行两个写入：更新业务表，以及追加一条追溯记录。追溯表只新增不修改，因此链路回看结果可信，这也是追溯查询页面能够还原完整时间线的基础。

入口有三个：管理界面点击操作、接口直接调用、pytest 用例自动执行。

### 链路二：设备数采链路

```
   模拟器（Modbus 从站，寄存器内存）
              ↓  轮询读取（Modbus TCP，端口 5020）
           采集器（格式转换）
              ↓  HTTP POST /api/device-data
   MES 质量判定（可解析性 → 工况区间 → 时间合理性）
              ↓
   写业务库 mes，不合格数据标记留痕
```

设备不主动推送数据，由采集器周期性轮询读取。质量判定依次经过三层校验，任一层不通过的数据会被标记并保留原始记录，不做静默丢弃。

### 链路三：测试验证链路

```
   pytest 用例
              ↓  调用 MES 接口造数
   写测试库 mes_test（与业务库物理隔离）
              ↓
   双向断言：接口返回正确性 + 直连数据库校验
              ↓
   执行结束自动清场（精确删除 + 时间窗兜底扫描）
```

测试过程会生成大量数据，写入业务库会影响人工查看与演示。测试库与业务库结构一致但物理隔离，框架在启动前会强制校验库名合规且接口写入库与校验库为同一实例。

### 三条链路对照

| 链路 | 触发方 | 写入库 | 数据留存 |
|------|--------|--------|----------|
| 业务主链路 | 人工操作或接口调用 | `mes` | 留存，属真实业务数据 |
| 设备数采链路 | 采集器自动轮询 | `mes` | 留存，含异常数据留痕 |
| 测试验证链路 | pytest 或 CI 触发 | `mes_test` | 不留，执行结束清场 |

## 三、启动顺序

### 顺序与依赖

```
① MySQL 服务           常驻运行，通常无需干预
② mes-platform         需等待就绪，约 20 至 40 秒
③ 以下三个按需启动，互不依赖：
     mes-console       查看界面
     mes-simulator     产生设备数据
     mes-autotest      执行测试
```

启动第三组任一工程前，需确认第二组已就绪。就绪状态可通过以下地址确认，返回体中 `status` 为 `UP` 且 `database` 为 `UP` 即表示可用：

```
http://127.0.0.1:8080/api/ready
```

被测系统尚未就绪时启动其余工程，会因连接失败产生大量难以解读的报错，先确认就绪状态可减少排查成本。

### 服务地址

| 角色 | 地址 | 说明 |
|------|------|------|
| MES 后端 | `http://127.0.0.1:8080` | 接口根地址 |
| 接口文档 | `http://127.0.0.1:8080/swagger-ui.html` | Swagger UI，可直接发起真实请求 |
| 管理界面 | `http://localhost:5173` | `npm run dev` 启动 |
| Modbus 设备 | `127.0.0.1:5020` | 模拟的 PLC 从站，需专用客户端读取 |

## 四、IDE 配置

### 工程与 IDE 的对应关系

| 工程 | 推荐 IDE | 说明 |
|------|----------|------|
| `mes-platform` | IntelliJ IDEA | 需 Maven、Spring Boot 支持 |
| `mes-autotest` | PyCharm | 需 Python 与 pytest 支持 |
| `mes-simulator` | PyCharm | 需 Python 支持 |
| `mes-console` | IDEA 或 PyCharm 均可 | 两者均提供 Vue 与 Node.js 支持 |

四个工程分别作为独立项目打开，不要将整个工作区作为单一项目导入。

IDEA 默认不包含 Python 插件，因此两个 Python 工程需使用 PyCharm 打开。PyCharm 具备 Vue 与 Node.js 支持，前端工程使用任一 IDE 均可。

### mes-platform（IDEA）

1. 菜单「文件」→「打开」，选择 `mes-platform` 目录
2. 等待 Maven 依赖解析完成
3. 找到 `src/main/java/com/xwj/mes/MesPlatformApplication.java`
4. 运行 `main` 方法，或使用 `Ctrl+Shift+F10`

若启动时报端口占用，提示端口为 63164 一类的非默认值，说明环境中存在名为 `SERVER__PORT` 的变量被 Spring Boot 的宽松绑定识别为 `server.port`。在运行配置的「环境变量」中移除该变量即可，本地常规终端与 IDE 环境不存在此变量。

**启动 profile 决定服务连哪个数据库，这一点在跑测试时是关键。** `application.yml` 中的配置为：

```yaml
spring:
  profiles:
    active: ${MES_PROFILE:dev}      # 未设置环境变量时默认 dev
```

| profile | 连接的库 | 适用场景 |
|---------|----------|----------|
| `dev`（默认） | `mes` | 人工操作、界面演示 |
| `test` | `mes_test` | 执行自动化用例 |

IDEA 中启动时不会读取 shell 的环境变量，因此默认走 `dev`。**执行自动化用例前需要改成 `test`，否则测试会因为校验不到数据而终止**（框架会明确报出服务实际连的库）。

在 IDEA 中切换 profile 的步骤（界面为中文时的菜单名，括号内为英文界面对应项）：

| 步骤 | 操作 |
|------|------|
| 1 | 点顶部运行按钮左侧的下拉箭头，选「编辑配置(E)...」（Edit Configurations） |
| 2 | 左侧列表选中当前使用的启动配置，名称形如 `MesPlatformApplication` |
| 3 | 在右侧找「活动配置文件(A)」（Active profiles），填入 `test` |
| 4 | 若界面上没有这一栏，改用环境变量：点配置面板上方的「修改选项(M)」（Modify options），在弹出列表里勾选「环境变量」；随后在出现的「环境变量」输入框右侧点图标，新增一行，名称填 `MES_PROFILE`、值填 `test` |
| 5 | 点「确定」保存：停止当前正在运行的服务，再重新点运行 |

环境变量只在启动时读取，**改完必须重启服务**才会生效。重启后核对控制台，出现下面这行表示已切到 test：

```
The following 1 profile is active: "test"
```

> **一个实际影响**：一个服务实例只能连一个库。切成 `test` 后，管理界面读到的就是 `mes_test` 的数据（内容接近空），
> 演示时看不到业务库里的内容。若需要两者同时可用，见第五节末尾「同时运行两个实例」——那种做法不需要改动 IDEA 的任何配置。

### mes-autotest / mes-simulator（PyCharm）

**配置解释器**（仅需一次）：

菜单「文件」→「设置」（或 `Ctrl+Alt+S`）→「项目」→「Python 解释器」→「添加解释器」→「添加本地解释器」→「现有」，选择项目使用的 Python 解释器路径。

**执行测试**：在项目树中右键 `testcases` 目录，选择「运行 'pytest in testcases'」。执行单个用例时，点击用例方法左侧的运行图标。执行前请确认 MES 服务已切到 `test` profile。

**调试方式**：在目标代码行左侧点击设置断点，然后以调试模式执行。程序在断点处暂停，可查看变量值并单步执行，适用于排查逻辑问题。

**带参数运行**：菜单「运行」→「编辑配置」新建 Python 配置，将参数填入「形参」字段。以设备模拟器为例：

| 字段 | 值 |
|------|-----|
| Script path | `<工程路径>\run.py` |
| Parameters | 见下表 |
| Working directory | 工程根目录 |

常用参数：

| 参数 | 作用 |
|------|------|
| `--self-check` | 仅自检，不需要 MES 在运行，首次使用建议先执行 |
| `--list-faults` | 列出全部故障场景 |
| `--duration 30` | 运行 30 秒后自动退出 |
| `--fault temp_overheat` | 注入设备过热故障后运行 |
| 无参数 | 正常运行，持续上报数据 |

`verify.py` 为端到端验证脚本，同样可在 IDE 中直接运行，需 MES 已启动。

### 配置文件的路径解析

各工程的配置加载均基于脚本文件自身位置计算路径（使用 `Path(__file__).resolve()`），与当前工作目录无关，从任意目录执行都能正确读取配置。

例外是 pytest：其 `testpaths` 配置为相对路径，因此需要在工程根目录下执行。使用 IDE 运行 pytest 时工作目录默认为工程根目录，通常无需调整。

## 五、使用场景

### 查看系统界面

启动 `mes-platform` 与 `mes-console` 后访问 `http://localhost:5173`，包含总览、工单、质量、物料、追溯、设备数采六个页面。界面数据需要通过操作产生，若需预先具备数据，可先执行下一场景。

前端在 PyCharm 中启动的方式如下。**前置条件：MES 后端已启动，且使用 `dev` profile**（界面展示的是业务库 `mes` 的内容）。

**第一步：配置 Node 解释器。** 本机 Node 未加入系统 PATH，PyCharm 不会自动发现，运行 `npm` 配置时会提示
「Node 运行时：在 %PATH% 中未找到可执行文件」，此时「运行」按钮是灰的。需要手工指定 Node 位置。

方式一（推荐，一次配好所有配置）：菜单「文件」→「设置」（或 `Ctrl+Alt+S`）→「语言和框架」→「Node.js」→
在「Node 解释器(N)」点下拉框右侧的浏览按钮，选择下面的文件 → 点「确定」：

```
C:\Users\Administrator\.workbuddy\binaries\node\versions\22.22.2-3\node.exe
```

方式二（在运行配置窗口里直接改）：打开「编辑配置」窗口，找到「Node 运行时(N)」下拉框，点它右侧的 `...` 按钮，
选择上面同一个 `node.exe`。

两种方式效果相同。配置成功后，「软件包管理器」一栏会自动带出同目录下的 npm，红色错误提示消失，「运行」按钮变为可用。

**第二步：安装依赖（仅首次）。** 依赖已安装时可跳过（判断方法：`mes-console` 目录下存在 `node_modules`）。若需重装，在 PyCharm 内置终端执行 `npm install`。

**第三步：启动开发服务器。** 三种方式任选：

| 方式 | 操作 | 说明 |
|------|------|------|
| 从 package.json 启动（推荐） | 打开 `package.json`，在 `"dev": "vite"` 那一行左侧点击绿色三角 | 使用已配置的 Node 解释器，不依赖 PATH |
| 从项目树启动 | 右键 `package.json` →「显示 npm 脚本」→ 双击 `dev` | 同上 |
| 内置终端 | 终端执行 `npm run dev` | 若提示 npm 不是内部命令，说明终端未继承 Node 路径，改用上面两种方式 |

启动后终端会输出本地访问地址 `http://localhost:5173`，浏览器打开即可。

其他脚本：`npm run build` 构建生产产物到 `dist/`；`npm run preview` 预览构建产物（端口 4173）。

### 同时运行两个实例

一个服务实例只能连一个库，因此「一边演示界面、一边跑测试」需要起两个实例，用端口区分：

| 实例 | 端口 | profile | 用途 |
|------|------|---------|------|
| 实例 A | 8080 | `dev` | 管理界面读取业务库 `mes` 的数据 |
| 实例 B | 8081 | `test` | 自动化用例，数据写入 `mes_test` |

如果采用这种布局，**IDEA 里正在跑的那个实例不需要做任何修改**（它保持 dev / 8080 供界面使用），只需要额外起第二个实例给测试用。

在 IDEA 中配置第二个实例：菜单「运行」→「编辑配置」→ 左侧选中现有配置 → 点面板左上方的复制图标，
把副本改名为 `MesPlatformApplication-test`，然后只改两处：

| 配置项 | 实例 A（原配置，不改） | 实例 B（副本） |
|--------|------------------------|----------------|
| 环境变量（或「活动配置文件」） | 不加 `MES_PROFILE` | `MES_PROFILE=test` |
| 程序实参（Program arguments） | 不加 | `--server.port=8081` |

测试侧还需让框架指向 8081。打开 PyCharm 的「编辑配置」窗口，左侧选中 pytest 配置，在「环境:」一栏
（无此栏时点「编辑配置」窗口里的环境变量图标）新增：

```
MES_BASE_URL=http://127.0.0.1:8081
```

前端无需改动，它固定指向 8080（如需调整，通过 `MES_BASE_URL` 覆盖，见 `mes-console/README.md`）。

**如果不想这么复杂**，采用单实例轮流切换也完全可行：跑测试前把服务切成 `test`，演示前切回 `dev`。
切换后记得重新启动服务，并在执行 `pytest` 前确认 profile 已生效。

### 产生设备数据

```bash
cd mes-simulator
python run.py
```

设备开始运转并持续向 MES 上报数据。运行后可在界面的设备数采页面观察到数据增长，异常数采记录中可看到被判定为可疑或异常的数据。

演示故障识别：

```bash
python run.py --fault temp_overheat      # 上报 512℃，判定为可疑
python run.py --fault sensor_fault       # 上报 ####，判定为异常且不入账
```

### 验证代码改动

```bash
cd mes-autotest
pytest                        # 全量 99 条
pytest -m smoke               # 冒烟 10 条
pytest -m "not db"            # 不需要数据库的 39 条

python tools/run.py           # 执行用例并生成三类报告
```

报告产物位于 `mes-autotest/reports/`，包含 HTML 报告、通过率趋势与 Allure 报告。

### 完整演示流程

按以下顺序操作可完整展示系统能力：

1. 确认 MySQL 服务处于运行状态
2. 启动 `mes-platform`，等待 `/api/ready` 返回 UP
3. 启动 `mes-console`，浏览六个页面的功能构成
4. 在界面上创建工单、执行派工与报工，展示业务链路
5. 启动 `mes-simulator`，展示设备数据自动流入
6. 使用 `--fault` 参数注入故障，回到设备数采页面观察识别结果
7. 执行 `pytest`，展示 99 条自动化用例的执行结果

第 6 步展示的不只是数据流通，还包括系统对异常数据的拦截与留痕能力，能够体现数据质量把控的完整程度。

## 六、常见问题

| 现象 | 原因与处理 |
|------|-----------|
| pytest 报「环境校验失败：经接口建的工单，在校验库里查不到」 | **最常见的问题**。MES 服务连的不是 `mes_test`。报错信息里会指出实际落点库（如 `mes`）并自动清理探针。按第四节把服务切到 `test` profile 后重跑即可 |
| pytest 报「拒绝执行：db.database 不是测试库」 | `mes-autotest/config/env.yml` 里的库名不以 `_test` 结尾。这是防止测试数据写进业务库的护栏，改回 `mes_test` |
| 界面可打开但全部请求失败，顶部显示后端不可用 | 后端未启动或未就绪。检查 `http://127.0.0.1:8080/api/ready` |
| 后端启动报端口 63164 被占用 | 环境变量 `SERVER__PORT` 被识别为服务端口。在运行配置中移除该变量 |
| pytest 报无法连接 | 后端未启动，或未监听 8080 端口 |
| 测试执行结束数据仍然存在 | 检查是否设置了 `MES_TEST_CLEANUP=false`，该变量用于保留现场 |
| 模拟器报端口 5020 被占用 | 上一次进程未正常退出。可修改 `config/simulator.yml` 中的 `modbus.port` 更换端口 |
| 模拟器正常运行但界面无数据 | 采集器未连上 MES。先执行 `python run.py --self-check` 确认模拟器自身正常 |
| PyCharm 中 pytest 找不到用例 | 解释器未正确配置，或未将 `mes-autotest` 作为项目根目录打开 |
| PyCharm 中运行 npm 配置提示「Node 运行时：在 %PATH% 中未找到可执行文件」，运行按钮为灰色 | Node 未加入系统 PATH，PyCharm 找不到它。按第五节「查看系统界面」的第一步手工指定 Node 解释器即可 |
| PyCharm 终端提示 npm 不是内部或外部命令 | 同上原因。改用 package.json 左侧的运行图标启动（不依赖 PATH），或先配好 Node 解释器 |
| 界面图表显示空白 | 浏览器窗口尺寸变化后未触发重绘。刷新页面即可 |
