# 使用手册

本文档说明 MES 自动化测试平台的部署顺序、IDE 配置与常见问题处理。

---

## 一、工程角色

项目由四个工程组成，职责与依赖关系如下。

| 工程 | 定位 | 面向对象 | 技术栈 |
|------|------|----------|--------|
| `mes-platform` | 被测的业务系统 | 工单员、质检员、仓管等业务角色 | Java 17 + Spring Boot + MySQL |
| `mes-console` | 操作界面 | 同上，日常操作的入口 | Vue 3 + Element Plus |
| `mes-autotest` | 自动化测试用例库 | 测试与开发，用于验证规则未被破坏 | pytest + requests |
| `mes-simulator` | 产线设备模拟 | 为系统提供工业数据来源 | Python + Modbus TCP |

依赖关系为围绕被测系统展开的单向结构：

```
        MySQL（最先就绪）
           │
     mes-platform  ←── 核心，其余三个工程均依赖它
      ↑    ↑    ↑
      │    │    └── mes-simulator   向数采接口上报设备数据
      │    └─────── mes-autotest    调用接口并回查数据库
      └──────────── mes-console     读取数据供人工操作
```

`mes-platform` 与 MySQL 是运行前提，必须先就绪。其余三个工程互不依赖，可独立启停。

## 二、数据流通

系统内部运行三条数据链路，写入两个物理隔离的数据库。

### 链路一：业务主链路

```
   管理界面 / 接口调用 / 测试用例
              ↓
   创建工单 → 派工 → 批次绑定 → 报工 → 质检 → 关闭
              ↓
        写业务库 mes
              ↓
   同时追加一条追溯流水记录（只增不改）
```

每完成一步业务操作，系统同时执行两个写入：更新业务表，以及追加一条追溯记录。追溯表只新增不修改，因此链路回看结果可信，这也是追溯查询页面能够还原完整时间线的基础。

入口有三个：管理界面点击操作、接口直接调用、pytest 用例自动执行。

### 链路二：设备数采链路

```
   模拟器（Modbus 从站，寄存器内存）
              ↓  轮询读取（Modbus TCP，端口 5020）
           采集器（格式转换）
              ↓  HTTP POST /api/device-data
   MES 质量判定（可解析性 → 工况区间 → 时间合理性）
              ↓
   写业务库 mes，不合格数据标记留痕
```

设备不主动推送数据，由采集器周期性轮询读取。质量判定依次经过三层校验，任一层不通过的数据会被标记并保留原始记录，不做静默丢弃。

### 链路三：测试验证链路

```
   pytest 用例
              ↓  调用 MES 接口造数
   写测试库 mes_test（与业务库物理隔离）
              ↓
   双向断言：接口返回正确性 + 直连数据库校验
              ↓
   执行结束自动清场（精确删除 + 时间窗兜底扫描）
```

测试过程会生成大量数据，写入业务库会影响人工查看与演示。测试库与业务库结构一致但物理隔离，框架在启动前会强制校验库名合规且接口写入库与校验库为同一实例。

### 三条链路对照

| 链路 | 触发方 | 写入库 | 数据留存 |
|------|--------|--------|----------|
| 业务主链路 | 人工操作或接口调用 | `mes` | 留存，属真实业务数据 |
| 设备数采链路 | 采集器自动轮询 | `mes` | 留存，含异常数据留痕 |
| 测试验证链路 | pytest 或 CI 触发 | `mes_test` | 不留，执行结束清场 |

## 三、启动顺序

### 顺序与依赖

```
① MySQL 服务           常驻运行，通常无需干预
② mes-platform         需等待就绪，约 20 至 40 秒
③ 以下三个按需启动，互不依赖：
     mes-console       查看界面
     mes-simulator     产生设备数据
     mes-autotest      执行测试
```

启动第三组任一工程前，需确认第二组已就绪。就绪状态可通过以下地址确认，返回体中 `status` 为 `UP` 且 `database` 为 `UP` 即表示可用：

```
http://127.0.0.1:8080/api/ready
```

被测系统尚未就绪时启动其余工程，会因连接失败产生大量难以解读的报错，先确认就绪状态可减少排查成本。

### 服务地址

| 角色 | 地址 | 说明 |
|------|------|------|
| MES 后端 | `http://127.0.0.1:8080` | 接口根地址 |
| 接口文档 | `http://127.0.0.1:8080/swagger-ui.html` | Swagger UI，可直接发起真实请求 |
| 管理界面 | `http://localhost:5173` | `npm run dev` 启动 |
| Modbus 设备 | `127.0.0.1:5020` | 模拟的 PLC 从站，需专用客户端读取 |

## 四、IDE 配置

### 工程与 IDE 的对应关系

| 工程 | 推荐 IDE | 说明 |
|------|----------|------|
| `mes-platform` | IntelliJ IDEA | 需 Maven、Spring Boot 支持 |
| `mes-autotest` | PyCharm | 需 Python 与 pytest 支持 |
| `mes-simulator` | PyCharm | 需 Python 支持 |
| `mes-console` | IDEA 或 PyCharm 均可 | 两者均提供 Vue 与 Node.js 支持 |

四个工程分别作为独立项目打开，不要将整个工作区作为单一项目导入。

IDEA 默认不包含 Python 插件，因此两个 Python 工程需使用 PyCharm 打开。PyCharm 具备 Vue 与 Node.js 支持，前端工程使用任一 IDE 均可。

### mes-platform（IDEA）

1. `File` → `Open`，选择 `mes-platform` 目录
2. 等待 Maven 依赖解析完成
3. 找到 `src/main/java/com/xwj/mes/MesPlatformApplication.java`
4. 运行 `main` 方法，或使用 `Ctrl+Shift+F10`

若启动时报端口占用，提示端口为 63164 一类的非默认值，说明环境中存在名为 `SERVER__PORT` 的变量被 Spring Boot 的宽松绑定识别为 `server.port`。在运行配置的 `Environment variables` 中移除该变量即可，本地常规终端与 IDE 环境不存在此变量。

### mes-autotest / mes-simulator（PyCharm）

**配置解释器**（仅需一次）：

`File` → `Settings` → `Project` → `Python Interpreter` → `Add Interpreter` → `Add Local Interpreter` → `Existing`，选择项目使用的 Python 解释器路径。

**执行测试**：在项目树中右键 `testcases` 目录，选择 `Run 'pytest in testcases'`。执行单个用例时，点击用例方法左侧的运行图标。

**调试方式**：在目标代码行左侧点击设置断点，然后以 Debug 模式执行。程序在断点处暂停，可查看变量值并单步执行，适用于排查逻辑问题。

**带参数运行**：使用 `Run` → `Edit Configurations` 新建 Python 配置，将参数填入 `Parameters` 字段。以设备模拟器为例：

| 字段 | 值 |
|------|-----|
| Script path | `<工程路径>\run.py` |
| Parameters | 见下表 |
| Working directory | 工程根目录 |

常用参数：

| 参数 | 作用 |
|------|------|
| `--self-check` | 仅自检，不需要 MES 在运行，首次使用建议先执行 |
| `--list-faults` | 列出全部故障场景 |
| `--duration 30` | 运行 30 秒后自动退出 |
| `--fault temp_overheat` | 注入设备过热故障后运行 |
| 无参数 | 正常运行，持续上报数据 |

`verify.py` 为端到端验证脚本，同样可在 IDE 中直接运行，需 MES 已启动。

### 配置文件的路径解析

各工程的配置加载均基于脚本文件自身位置计算路径（使用 `Path(__file__).resolve()`），与当前工作目录无关，从任意目录执行都能正确读取配置。

例外是 pytest：其 `testpaths` 配置为相对路径，因此需要在工程根目录下执行。使用 IDE 运行 pytest 时工作目录默认为工程根目录，通常无需调整。

## 五、使用场景

### 查看系统界面

启动 `mes-platform` 与 `mes-console` 后访问 `http://localhost:5173`，包含总览、工单、质量、物料、追溯、设备数采六个页面。界面数据需要通过操作产生，若需预先具备数据，可先执行下一场景。

### 产生设备数据

```bash
cd mes-simulator
python run.py
```

设备开始运转并持续向 MES 上报数据。运行后可在界面的设备数采页面观察到数据增长，异常数采记录中可看到被判定为可疑或异常的数据。

演示故障识别：

```bash
python run.py --fault temp_overheat      # 上报 512℃，判定为可疑
python run.py --fault sensor_fault       # 上报 ####，判定为异常且不入账
```

### 验证代码改动

```bash
cd mes-autotest
pytest                        # 全量 99 条
pytest -m smoke               # 冒烟 10 条
pytest -m "not db"            # 不需要数据库的 39 条

python tools/run.py           # 执行用例并生成三类报告
```

报告产物位于 `mes-autotest/reports/`，包含 HTML 报告、通过率趋势与 Allure 报告。

### 完整演示流程

按以下顺序操作可完整展示系统能力：

1. 确认 MySQL 服务处于运行状态
2. 启动 `mes-platform`，等待 `/api/ready` 返回 UP
3. 启动 `mes-console`，浏览六个页面的功能构成
4. 在界面上创建工单、执行派工与报工，展示业务链路
5. 启动 `mes-simulator`，展示设备数据自动流入
6. 使用 `--fault` 参数注入故障，回到设备数采页面观察识别结果
7. 执行 `pytest`，展示 99 条自动化用例的执行结果

第 6 步展示的不只是数据流通，还包括系统对异常数据的拦截与留痕能力，能够体现数据质量把控的完整程度。

## 六、常见问题

| 现象 | 原因与处理 |
|------|-----------|
| 界面可打开但全部请求失败，顶部显示后端不可用 | 后端未启动或未就绪。检查 `http://127.0.0.1:8080/api/ready` |
| 后端启动报端口 63164 被占用 | 环境变量 `SERVER__PORT` 被识别为服务端口。在运行配置中移除该变量 |
| pytest 报无法连接 | 后端未启动，或未监听 8080 端口 |
| 测试执行结束数据仍然存在 | 检查是否设置了 `MES_TEST_CLEANUP=false`，该变量用于保留现场 |
| 模拟器报端口 5020 被占用 | 上一次进程未正常退出。可修改 `config/simulator.yml` 中的 `modbus.port` 更换端口 |
| 模拟器正常运行但界面无数据 | 采集器未连上 MES。先执行 `python run.py --self-check` 确认模拟器自身正常 |
| PyCharm 中 pytest 找不到用例 | 解释器未正确配置，或未将 `mes-autotest` 作为项目根目录打开 |
| 界面图表显示空白 | 浏览器窗口尺寸变化后未触发重绘。刷新页面即可 |
