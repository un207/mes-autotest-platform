# MES 管理台（mes-console）

> M4 交付物之二：Vue 3 管理界面，把 M1 的 24 个接口变成可操作的界面。

## 这是什么

前面三步做出的东西，只有开发和测试能看：M1 是后端接口、M2/M3 是自动化脚本与报告。
这一层是**给人用的界面** —— 工单员建单派工、质检员录质检、仓管管批次、运维看设备数据。

它同时是求职材料的"门面"：面试官点开链接就能看到系统在运行，不必读代码或看接口文档。

---

## 快速开始

**前置**：MES 后端必须已启动（界面本身不含数据）。

```bash
# 1. 启动后端（另开一个终端）
cd ../mes-platform
unset SERVER__PORT SERVER__HOST
export JAVA_HOME="C:/Users/Administrator/.jdks/temurin-17.0.20.1"
mvn spring-boot:run

# 2. 安装依赖并启动界面
cd ../mes-console
npm install
npm run dev          # 开发模式，http://localhost:5173
```

生产构建与预览：

```bash
npm run build        # 产物在 dist/
npm run preview      # 预览构建产物，http://localhost:4173
```

> 后端地址默认为 `http://127.0.0.1:8080`。换环境用 `MES_BASE_URL` 覆盖：
> `MES_BASE_URL=http://192.168.1.10:8080 npm run dev`

## 六个页面

| 页面 | 对应接口 | 做什么 |
|------|----------|--------|
| **总览** | 统计 3 个 + 异常数采 | 核心指标卡、产量日报图、低良率排行、异常数采清单 |
| **工单管理** | 工单 7 个操作 | 建单、派工、报工、关闭；详情抽屉带报工明细 |
| **质量管理** | 质检 5 个操作 | 质检录入（实时推演结论）、不良代码分布、按工单查不良明细 |
| **物料批次** | 批次 6 个操作 | 建档、绑定工单、出货消耗 |
| **追溯查询** | 追溯 2 个 | 正向（批次→流向）／反向（工单→用料+不良），时间线呈现链路 |
| **设备数采** | 数采 4 个操作 | 数采记录、异常原因分布、异常数据逐条排查 |

## 三个刻意的设计选择

**① 按钮按状态动态显示，而不是全摆出来等用户点了被拒。**
后端必须拦截非法流转（这是数据正确性的底线），但界面不该诱导用户去做必然失败的操作。
比如工单已关闭，界面上就不会再出现「报工」按钮。**界面负责让人做对的事，后端负责兜住做错的事。**

**② 规则前置到界面上，而不是只藏在报错里。**
质检录入时，填完数量就实时显示「系统会判成什么」以及为什么；
报工时实时校验「合格＋不良是否等于报工数」。
用户提前知道规则，比提交后被拒再猜原因好得多。

**③ 状态与文案的映射只有一份（`src/utils/dict.js`）。**
`NEW` / `DISPATCHED` 这类英文码在列表、详情、标签、筛选项里到处出现。
如果每处各写一份中文映射，改一处漏一处，界面就会出现同一状态两种叫法。

## 两个实现细节

**请求走相对路径 `/api`**，开发期由 vite proxy 转发到后端。
好处是不用在前端代码里配 CORS（虽然后端已开白名单），换环境也不用改代码。

**构建产物做了分包**：`vue` / `element-plus` / `echarts` 各自独立。
这三个库体积大且极少变动，单独分包后浏览器能长期缓存 ——
改业务代码（业务包仅约 71KB）不会让用户重新下载那 2MB 的三方库。

## 已知边界

- 无登录与角色权限：谁打开都能操作。后端权限体系尚未实现（M1 的既定范围）
- 无国际化：界面只有中文
- 表格未做虚拟滚动：数据量大（数千行以上）时列表会变慢，当前数据规模不受影响
- 未做移动端适配：工业管理界面以桌面为主，只在宽度 <992px 时做了基础换行
