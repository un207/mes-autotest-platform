# MES 设备模拟器（mes-simulator）

> MES 自动化测试平台项目的 **M4 交付物之一**。以 Modbus TCP 模拟产线设备，向 MES 数采接口上报数据，并提供故障注入能力以验证质量把关逻辑。

## 工程定位

MES 的数采入口实现了三层质量把关：可解析性、工况区间、时间合理性。这三层逻辑只有在接收到异常数据时才会被执行。若数据源始终只上报正常值，相关分支永远不被覆盖，把关逻辑的正确性无从验证。

因此本工程承担两项职责：

1. **提供一台运行时变化的设备**：产量按生产节拍递增，温度围绕基准随机游走，超过上限时自动转入故障态。数据通过 Modbus 协议被读取，而非直接构造请求。
2. **提供一套故障注入器**：覆盖六种真实故障形态，逐一验证 MES 能否识别、标记是否正确、判定原因是否指向准确。

第二项职责使这个工程区别于普通的接口造数脚本：它验证的是被测系统的判定能力，不只是数据通路。

---

## 工业链路结构

```
  设备（Modbus 从站）  ←──轮询读取──  采集器  ──HTTP 上报──→  MES 数采接口
      寄存器内存                  格式转换 + 故障注入           质量判定 + 落库
```

这条链路反映的是工业现场的实际形态：设备不主动推送数据，只负责把值写入寄存器。中间必须存在一层采集程序（现场通常称网关或 SCADA），周期性读取寄存器、转换为业务系统可接收的格式后上报。

本工程的代码即该层网关的最小实现。理解这一结构是理解 OT（工业现场）与 IT（业务系统）边界的前提，也是为何本工程内部分为服务端与采集器两个角色，而不是让模拟器直接调用 MES 接口。

## 1. 安装与自检

```bash
pip install -r requirements.txt

python run.py --self-check     # 自检，不需要 MES 在运行
```

自检依次验证三项内容：Modbus 读写通路是否可用、设备逻辑是否在推进（产量是否增长）、故障注入能否正确修改寄存器并恢复。

依赖中的 `pyserial` 为必需项而非可选。pymodbus 3.16 的 transport 层在模块加载时无条件导入 `serialtransport`，缺少该依赖时即使只使用 TCP 模式，`import pymodbus.server` 也会直接失败并报出 `NameError: pyserial is not defined`。

## 2. 运行方式

| 命令 | 用途 |
|------|------|
| `python run.py` | 正常运行，设备运转并持续上报 |
| `python run.py --duration 30` | 运行 30 秒后自动退出，便于脚本化验证 |
| `python run.py --fault <key>` | 注入指定故障场景后运行 |
| `python run.py --list-faults` | 列出全部故障场景及预期判定 |
| `python run.py --self-check` | 仅自检，不连接 MES |
| `python run.py --no-collect` | 仅运行设备逻辑，不上报 |
| `python verify.py` | 端到端验证，需 MES 已启动 |

```bash
# 正常运行（需要 MES 已启动）
python run.py

# 注入设备过热故障
python run.py --fault temp_overheat

# 只观察设备动作，不上报
python run.py --no-collect
```

## 3. 与 MES 的对接方式

采集器与 MES 之间的对接通过 MES 的数采上报接口完成，涉及三个环节。

### 上报报文的构造

每条上报包含设备编号、产线编号、指标类型、原始值、单位与采集时间：

```python
{
    "equipmentCode": "SIM-LASER-01",
    "lineCode": "SIM-LINE-A",
    "metric": "TEMPERATURE",
    "rawValue": "25.5",
    "unit": "℃",
    "collectTime": "2026-10-12 14:49:14"
}
```

`rawValue` 采用字符串类型，与 MES 接口的声明保持一致。这样设计的原因是现场设备上报畸形数据属于常态，入口不做类型强转，质量判定交由业务层完成——采集器只负责如实上报读到的值。

### 寄存器值到上报值的转换

寄存器存放的是 16 位整数，与工程值之间存在缩放关系。转换规则来自点表（`mes_sim/registers.py`），服务端写入与采集端读取共用同一份定义，避免两侧各写一套映射导致不一致：

```python
class RegisterPoint:
    address: int
    name: str
    metric: Metric | None
    unit: str
    scale: float          # 0.1 表示寄存器以 0.1 为单位存储（255 对应 25.5℃）

    def to_engineering(self, raw: int) -> float:
        return round(raw * self.scale, 4)
```

### 批量读取

采集器读取整块寄存器后按点表拆分为多个指标，逐一上报。读取操作使用单次请求覆盖全部点位，而非逐点读取，以减少协议往返次数。

设备侧与 MES 的数据流向是单向的：采集器读取寄存器后上报，不向设备回写任何业务判断。工况是否越界、数据是否可用，全部由 MES 判定。这样做保证质量判定的口径只有一个定义处，不会出现两侧各判一套、结论不一致的情况。

## 4. 故障场景

故障注入分两层，分层的依据是协议本身的表达能力而非设计偏好。

**设备侧注入（修改 Modbus 寄存器）。** 保持寄存器为 16 位无符号整数，无法表示负数和大于 65535 的值。因此只有落在 0 至 65535 区间内的非法工况值可以通过这一层注入。

| 场景 | 注入内容 | 预期 MES 判定 |
|------|----------|---------------|
| `temp_overheat` | 温度寄存器置 5120，即 512℃ | 可疑，超出 -50 至 200℃ 区间 |
| `status_illegal` | 运行状态置 99 | 可疑，超出 0 至 10 区间 |

**采集侧注入（修改上报字符串）。** 现场传感器故障时设备无法提供有效值，网关上报的是错误标记串；超出 16 位表示能力的场景也只能在这一层构造。

| 场景 | 注入内容 | 预期 MES 判定 |
|------|----------|---------------|
| `sensor_fault` | 上报 `####` | 异常，不可解析，数值不入账 |
| `garbage_value` | 上报 `12x3` | 异常，不可解析，数值不入账 |
| `output_over_limit` | 上报 `1000001` | 可疑，超出 0 至 1000000 区间 |
| `clock_drift` | 采集时间超前 2 小时 | 可疑，判定为设备时钟异常 |

两类注入对应真实故障形态：前者是工况越界但数据本身有效，后者是设备侧已无法产出有效数据。MES 对两者的处理不同——越界数据仍留档，不可解析的数据不入账但保留原始串，这一区别由 `verify.py` 逐项验证。

## 5. 端到端验证

`verify.py` 是 M4 的验收脚本，覆盖四种情况：

1. **基线**：无故障时上报，三种指标均应判为正常
2. **异常识别**：逐个注入六个场景，各自应判定出预期的标记与原因，原因文本需命中预设关键词
3. **恢复**：撤销注入后再次上报，应回到正常状态，证明注入未对后续数据造成残留影响
4. **可追溯**：MES 的异常清单应能捞取到本轮注入的数据

仅验证「上报成功」不足以说明把关有效：全部数据被判正常意味着把关形同虚设，全部被判异常则意味着阈值设置过严。三种判定结果都需要覆盖。

```bash
python verify.py
```

## 6. 寄存器点表

地址与业务含义的映射集中在 `mes_sim/registers.py`，服务端写入与采集端读取共用。

| 地址 | 点名 | 含义 | 上报指标 | 单位 | 缩放 |
|------|------|------|----------|------|------|
| 0 | OUTPUT_COUNT | 累计产量 | OUTPUT | 件 | 1 |
| 1 | RUN_STATUS | 运行状态 | STATUS | — | 1 |
| 2 | TEMPERATURE | 设备温度 | TEMPERATURE | ℃ | 0.1 |
| 3 | QUALIFIED_COUNT | 累计良品 | 设备自身状态，不上报 | 件 | 1 |
| 4 | DEFECTIVE_COUNT | 累计不良 | 设备自身状态 | 件 | 1 |
| 5 | CYCLE_TIME | 生产节拍 | 设备自身状态 | 秒 | 1 |
| 6 | RUN_MINUTES | 运行时长 | 设备自身状态 | 分钟 | 1 |
| 7 | FAULT_CODE | 故障代码 | 设备自身状态 | — | 1 |

前三项与 MES 的三种数采指标一一对应，其余为设备内部状态，用于诊断与故障注入，不参与上报。

`scale` 字段的存在同样受协议约束：寄存器无法存储浮点数，现场通行做法是将工程值乘以倍数后以整数存储（25.5℃ 存为 255），采集端再还原。这是协议表达能力限制下的必然处理方式。

## 7. 设备行为模型

设备行为定义在 `mes_sim/device.py`，模拟真实设备的运行特征以便产生可信的数据形态。

| 特征 | 实现方式 |
|------|----------|
| 产量递增 | 按生产节拍累积，非匀速增长，附带余数累加 |
| 温度变化 | 随机游走叠加向基准值的回归，避免数值无限漂移 |
| 过热保护 | 温度超过上限时自动转入故障态，对应真实设备的保护逻辑 |
| 状态迁移 | 停机、运行、故障三态；停机时温度缓慢回落至环境温度 |
| 良品与不良 | 按设定的不良率随机分配，使良率统计有实际意义的波动 |

随机数使用可注入的 `Random` 实例，测试时给定种子即可复现同一串数据，便于对照排查。

## 9. 实现说明

**Modbus 服务端的数据结构选择。** pymodbus 3.16 重构了 datastore 层：旧接口（`ModbusDeviceContext`、`ModbusSequentialDataBlock`）已被标记为弃用并计划在 v4 移除；新接口（`SimData`、`SimDevice`）是官方推荐方向，但面向静态仿真配置设计，`SimData` 的值在构建期确定，未提供运行时的写入接口。

设备模拟器需要在运行过程中修改寄存器值（产量增长、温度波动），因此 `server.py` 采用了一条折中路径：通过 `SimRuntime` 内部持有的寄存器列表引用来实时改值。该引用与服务端读取的是同一块内存，修改立即生效。

这条路径依赖一个内部结构，因此集中封装在 `ModbusDeviceServer.registers` 属性中。将来 pymodbus 升级若变更该结构，受影响的范围仅限这一处，且启动自检会立即报错，不会延迟到采集阶段才表现为读到空值。

**服务的可用性判定。** 服务端启动成功不代表客户端能够读取数据，端口占用、unit_id 不匹配、寄存器块未正确挂载都会导致服务处于假活状态。因此 `self_check` 在启动后使用真实客户端执行一次写入并回读，确认读写通路完整。

## 10. 已知边界

- 仅实现功能码 3（读保持寄存器）的读取路径，可满足当前设备模拟需求；真实设备还会使用线圈与输入寄存器
- 当前为单设备实现。Modbus 支持一个网关下挂多台从站（通过 unit_id 区分），代码结构支持扩展但未启用
- 不做连接鉴权与加密，Modbus TCP 协议本身也未提供该能力，这也是工业网络需要依赖物理隔离与防火墙的原因
- 采集器按固定周期轮询，未实现断线重连与失败退避。真实网关必须处理设备离线场景，此处为简化实现
