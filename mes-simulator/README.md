# MES 设备模拟器（mes-simulator）

> M4 交付物之一：用 **Modbus TCP** 模拟产线设备，把数据送进 MES 数采接口，并**主动注入异常数据**验证质量把关。

## 它解决什么问题

MES 的数采入口做了三层质量把关（可解析性 → 工况区间 → 时间合理性）。
如果模拟器永远只发正常数据，这三层逻辑就从未被真正走通过 —— 写了等于没写。

这个模拟器同时提供两样东西：

1. **一台会动的设备**：产量按节拍递增、温度随机游走、过热自动停机，数据经 Modbus 协议被读取
2. **一套异常注入器**：6 种真实故障形态，逐个验证 MES 是否真的拦得住

---

## 为什么要有这一层（工业链路的真实形态）

```
  设备（Modbus 从站）  ←──轮询读取──  采集器  ──HTTP 上报──→  MES 数采接口
      寄存器内存                  格式转换 + 异常注入           质量判定 + 落库
```

设备**不会主动推送**数据，它只负责把值放进寄存器。中间必须有一层采集程序（现场叫网关/SCADA）
周期性地去读、转成业务系统能收的格式再上报。本项目这段代码就是那层网关的最小实现 ——
这是理解 OT（工业现场）与 IT（业务系统）边界的关键。

## 快速开始

### 1. 安装依赖

```bash
pip install -r requirements.txt
```

> **注意**：`pyserial` 是必需项。pymodbus 3.16 的 transport 层无条件导入 `serialtransport`，
> 缺 pyserial 时**连 TCP 模式都 import 不了**（报 `NameError: pyserial is not defined`）。

### 2. 自检（不需要 MES，先确认模拟器本身没问题）

```bash
python run.py --self-check
```

会依次验证三件事：Modbus 读写通路、设备逻辑是否在推进（产量增长）、异常注入能否改到寄存器。

### 3. 运行（需要 MES 已启动）

```bash
# 起设备 + 采集上报，持续运行
python run.py

# 跑 30 秒后自动退出
python run.py --duration 30

# 注入指定异常场景
python run.py --fault temp_overheat

# 只看设备动作、不上报
python run.py --no-collect
```

### 4. 端到端验证（这是 M4 的验收手段）

```bash
python verify.py
```

它会依次验证：基线数据判正常 → 6 个异常场景各自被判出预期标记 → 撤销后回到正常 → 异常清单可捞取。

| 命令 | 用途 |
|------|------|
| `python run.py` | 正常运行（设备 + 采集上报） |

## 异常场景清单

分两层注入 —— 这不是为了复杂，而是协议限制决定的：

**① 设备侧（改 Modbus 寄存器）**：保持寄存器是 16 位无符号整数，**装不下负数和超过 65535 的值**。
所以只有"在 0~65535 范围内的非法工况值"能从这里注入。

| 场景 | 注入内容 | 预期 MES 判定 |
|------|----------|---------------|
| `temp_overheat` | 温度寄存器置 5120（=512℃） | 可疑（超出 -50~200℃） |
| `status_illegal` | 运行状态置 99 | 可疑（超出 0~10） |

**② 采集侧（改上报的原始串）**：现场传感器故障时设备没有有效值可给，网关上报的是错误标记串；
"产量超一百万"这种也超出 16 位表示能力，只能在这一层构造。

| 场景 | 注入内容 | 预期 MES 判定 |
|------|----------|---------------|
| `sensor_fault` | 上报 `####` | 异常（不可解析，数值不入账） |
| `garbage_value` | 上报 `12x3` | 异常（不可解析，数值不入账） |
| `output_over_limit` | 上报 `1000001` | 可疑（超出 0~1000000） |
| `clock_drift` | 采集时间超前 2 小时 | 可疑（设备时钟异常） |

## 寄存器点表

地址 → 业务含义的唯一映射来源，服务端与采集端共用（避免两边各写一份、迟早对不上）。

| 地址 | 点名 | 含义 | 上报指标 | 单位 | 缩放 |
|------|------|------|----------|------|------|
| 0 | OUTPUT_COUNT | 累计产量 | OUTPUT | 件 | 1 |
| 1 | RUN_STATUS | 运行状态 | STATUS | — | 1 |
| 2 | TEMPERATURE | 设备温度 | TEMPERATURE | ℃ | 0.1 |
| 3 | QUALIFIED_COUNT | 累计良品 | 设备自身状态，不上报 | 件 | 1 |
| 4 | DEFECTIVE_COUNT | 累计不良 | 设备自身状态 | 件 | 1 |
| 5 | CYCLE_TIME | 生产节拍 | 设备自身状态 | 秒 | 1 |
| 6 | RUN_MINUTES | 运行时长 | 设备自身状态 | 分钟 | 1 |
| 7 | FAULT_CODE | 故障代码 | 设备自身状态 | — | 1 |

**关于 `scale=0.1`**：Modbus 寄存器存不了浮点，现场惯例是把工程值乘以倍数存整数
（温度 25.5℃ 存 255），采集端再除回来。这不是偷懒，是协议本身的限制决定的。

## 工程结构

```
mes-simulator/
├── config/
│   └── simulator.yml        # 端口、设备工况、采集周期
├── mes_sim/
│   ├── registers.py         # 点表：地址 ↔ 业务含义的唯一映射
│   ├── device.py            # 设备行为模型（产量递增、温度游走、过热停机）
│   ├── server.py            # Modbus TCP 从站
│   ├── collector.py         # 采集器（轮询寄存器 → 上报 MES）
│   └── faults.py            # 异常注入器
├── run.py                   # 运行入口
└── verify.py                # 端到端验证
```

## 一个需要说明的技术选择

pymodbus **3.16 把 datastore 层重构了**：旧 API（`ModbusDeviceContext` / `ModbusSequentialDataBlock`）
官方已标记弃用、v4 将移除；新 API（`SimData`/`SimDevice`）是官方方向，但它是为**静态仿真配置**设计的 ——
`SimData` 的值在构建期确定，没有公开的运行时写入接口。

而设备模拟器必须在运行中改寄存器（产量要增长、温度要波动）。所以 `server.py` 里用了一条折中路径：
借 `SimRuntime` 内部持有的寄存器列表引用来实时改值。

这条路径只依赖一个内部结构，并集中收在 `ModbusDeviceServer.registers` 属性里 ——
将来 pymodbus 升级若破坏它，只会坏这一处，且自检会立刻报出来（而不是等采集时才发现读到的是空值）。

## 已知边界（如实说明）

- 只实现了**功能码 3（读保持寄存器）**的读取路径。设备模拟场景够用，但真实设备还会用到线圈、输入寄存器等
- **单设备**。Modbus 支持一个网关下挂多台从站（靠 unit_id 区分），代码结构支持扩展但当前只起了一台
- 不做连接鉴权与加密（Modbus TCP 协议本身也不提供）——这也是为什么工业网络必须靠物理隔离与防火墙
- 采集器按固定周期轮询，未做断线重连与失败退避。真实网关必须处理设备离线，这里是简化版
